# 30 条判定用例（cases.md）

> **这份文件解决一件事**：把"判得对"变成可回归、可打假的证据。每条用例是一条**人工先标注**的轨迹，系统必须判出同样结论；CI 每次提交都跑，改坏立刻红。
> **出处**：`科目二扣分规则表-对内版.md` 第 9 节。规则编号以该文件第 2 节为准。
> 状态：v1.0（2026-11-16）。**30 条编号已定。**

---

## 1. 编号规则

`项目代号-类别-序号`

| 项目代号 | 项目 | | 类别代号 | 含义 |
|---|---|---|---|---|
| `RP` | 倒车入库 | | `STD` | 标准通过（对照组） |
| `PP` | 侧方停车 | | `BODY` | 车身出线 |
| `HS` | 坡道定点停车与起步 | | `NOTIN` | 倒车不入 |
| `SC` | 曲线行驶 | | `STOP` | 中途停车 |
| `RA` | 直角转弯 | | `TIME` | 超时 |
| | | | `ORD` / `SIG` | 顺序错 / 转向灯 |
| | | | `POLE` / `FIX` / `SIDE` / `ROLL` | 碰桩 / 定点 / 右侧距 / 后溜 |
| | | | `PEN*` / `EDGE` / `SUS` | 压线 / 擦线 / 持续压线 |

**为什么是这种分法**：原方案"5 项目 × 6 类（标准/压线/出线/停车/超时/顺序）"里，曲线没有超时、直角没有顺序，硬套会凑出 4 条无意义用例。改成每个项目按**它自己真实的规则集**选 6 类，正好 30 条，且 R01—R13 每条至少被覆盖一次。

## 4. 每条用例的数据形态

一个文件同时含轨迹与人工标注，放在 `cases/<用例编号>/`：

```
cases/RP-BODY-01/
├── trajectory.json   # 帧序列：t, x, y, theta, v, delta, gear, signal
├── expected.json     # 人工标注的期望结论
└── note.md           # 一句话说明这条测什么、为什么这样造
```

`expected.json` 最小字段：

```jsonc
{
  "caseId": "RP-BODY-01",
  "project": "reverse_park",
  "verdict": "fail",           // pass | fail | deduct
  "score": null,               // 扣分项填 95/90 这类
  "violations": [{ "ruleId": "R01", "part": "右后轮", "tStart": 42.30 }],
  "labeledBy": "林呈睿",       // ← 人工标注必须有署名和日期
  "labeledAt": "2026-12-XX",
  "basis": "GA 1026—2022 倒车入库·车身出线"
}
```

> **`labeledBy` 不能空。** 硬指标要求"30 段操作人工先判、系统再判，结论完全一致"——先判的那一方是谁、什么时候判的，必须留痕，否则这条用例在答辩时不成立。

## 5. 回归口径

| 项 | 要求 |
|---|---|
| 通过标准 | **30/30**，一条不允许失败 |
| 运行环境 | node，无 DOM（判定层不依赖渲染） |
| 触发时机 | 每次 push，CI 自动跑 |
| 失败输出 | 打印 `caseId` + 期望 + 实际 + 首个不一致字段 |
| 容差测试 | 另跑一组：把轨迹采样人为降到 5Hz，要求开扫掠漏检率 0%、关扫掠漏检率 > 0 |

**最后一条不是锦上添花，是硬指标要求**（"把记录频率从每秒 20 次降到 5 次，仍不漏判任何一次压线"）。它同时也是"扫掠模块到底有没有用"的唯一证据——证明有用，比声称有用强。
